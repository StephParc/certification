    Dépendances:

    Cette partie nécessite une clé pour l'utilisation de l'API Ticketmaster. Pour cela, il faut créer une application à l'adresse suivante:
    https://developer.ticketmaster.com/

    Description:

    Pour réaliser cette partie tout comme E6, j'ai utilisé Dbt. La documentation est à l'adresse https://docs.getdbt.com/.
    Les données proviennent de l'API Ticketmaster.
    Dbt se concentre essentiellement sur la transformation sql (partie T de ELT). Tous les fichiers sont donc des .sql et des .yml.
    Le principe: on paramètre les sources de données, on définit des modèles (associés à des schémas = schémas bases de données) et chaque script dans un modèle est une table ou une vue générée. Tous les .sql du projet sont exécutés en une fois avec la commande dbt run, l'ordre étant géré par Dbt en fonction des dépendances déclarées.
    L'extraction et le chargement sont faits en amont par d'autres outils, scripts python pour ce projet qui se trouve dans le dossier E5.

    Ainsi, ticketmaster_harvester.py effectue l'appel API et stocke dans le data lake, load_to_db.py découpe les événements collectés en payload JSONB pour Postgres. Ces deux scripts sont prévus pour une exécution quotidienne.
    Les deux autres ingest_ticketmaster.py et load_ticketmaster_to_pg.py sont leurs pendants de masse pour constituer un volume de données initial. Ils ne sont pas orchestrés et sont exécutés manuellement de date à date.

    stg_ticketmaster.sql transforme les données raw obtenues en découpant le payload et en typant au besoin.
    dim_dates.sql, dim_genres.sql, dim_venues.sql et facts_events.sql* les répartissent avec les agrégations voulues pour dégager les axes d'analyses (temporel, géographique et stylistique). Par assurer l'unicité de clé, j'ai utilisé des surrogate_key (hachage de clés composites)

    Le dossier analyses stocke des requêtes SQL. Elles permettent un aperçu du résultat avec la commande dbt show --select nom_de_l_analyse qui par défaut est limité à 5 lignes. Il est possible de modifier ce nombre par l'ajout de --limit nb_lignes_souhaité. Ces requêtes sont traduites pour Postgres par la commande dbt compile, qui génère le script dans le dossier target/compiled/nom_du_projet/analyses.

    Par défaut, Dbt préfixe les tables et vues du nom du schéma concatené. Pour contrer ce comportement, on crée une macro personnalisée generate_schema_name (dans le dossier macros).

    Dans les dossiers models, les fichiers de configurations .yml définissent les sources (extérieures au projet dbt) et les models. Ceux-ci permettent la description des colonnes, le type et les tests directs sur celles-ci (non null, seuils de valeurs, conformes à une liste,...). D'autres tests plus complexes (unicité, portant sur plusieurs colonnes ou tables,...) peuvent être ajoutés dans le dossier tests/. Ces requêtes tests personnalisées sont formulés pour ne renvoyer aucune ligne. Tous sont exécutés avec dbt test. Pour cela, des packages supplémentaires peuvent être nécessaires et sont à mentionner dans packages.yml.

    Enfin, dbt_project.yml et profiles.yml définissent les modèles globaux pour l'un et les connexions aux sources pour l'autre.

    Le schéma raw ainsi que la table (source pour Dbt), les rôles et les droits sont crées par le script setup_ticketmaster.sql, exécuté par setup_infra.sh.

    Orchestration:

    L'orchestration quotidienne de ces flux se fait par ticketmaster_etl_pipeline.py:
    appel API -> stockage dans le data lake -> ingestion dans le data warehouse
