    Partie E4: Réalisation d'un service numérique

    Objet: Cette partie a pour objet l'exposition par API des données collectées via plusieurs sources: fichier plat, API, scraping, BDD et big data.

    Les dépendances sont dans le pyproject.toml

    Description des sous-parties:

    Le scraping

    Le scraping se fait à l'aide de Scrapy sur le site musicshopeurope.com, avec comme critères de sélection la formation (orchestre d'harmonie) et les partitions comprenant un conducteur.
    Cette sous-partie du projet est dans le répertoire E4/harmonie/harmonie.
    La documentation de Scrapy se trouve à l'adresse: https://www.scrapy.org

    Le script principal est hbm_scrap.py. La méthode parse() permet la navigation jusqu'aux pages scrapées tandis que parse_partition() en cible les éléments html. On obtient un objet item instance de la classe HarmonieItem définie dans items.py.
    Le fichier middleware.py conserve son paramétrage par défaut.
    Dans settings.py, il faut compléter le USER_AGENT avec ses propres informations.
    Le pipelines.py permet de nettoyer les données extraites et éventuellement de les insérer en base de données.
    Le temps d'exécution pour ce projet étant très important, un découpage par blocs de 100 pages (1h de scraping environ) est privilégié et l'insertion ne se fait pas via le pipeline.

    Du fait du choix d'une plage de pages fixe à scraper (10 prévues initialement couvrant plusieurs mois de nouveautés, réduit à une avec une fréquence d'orchestration adaptée), le fichier musicshop_last.csv généré contient des doublons. Pour éviter de les traiter au moment de l'insertion en base de données, ce traitement est séparé: comparaison des deux fichiers, les différences (ajouts) sont insérées dans un fichier musicshop_AAAA-MM-DD.csv, enregistré dans un dossier archives, ainsi que dans le fichier musicshop_all.csv qui constitue le cumul des entrées (chargés dans le datalake).
    Le fichier musicshop_last.csv est conservé en l'état jusqu'au prochaine scraping et le fichier musicshop_new.csv ne contient que les nouveautés qui seront insérées.

    Les données sont ensuite chargées dans la BDD.

    L'API externe

    Parmi les sources requises pour ce projet fingure une API: celle de MusicBrainz.org.
    Le site musicshopeurope.com ne permet pas de scraper séparément le nom et le prénom d'un auteur. L'API récupère cette information ainsi que d'autres complémentaires à partir du nom complet.
    Dans le script api_externe.py, la fonction get_api_externe() fait ce traitement.
    Cette sous-partie du projet est dans le répertoire E4/harmonie/BDD.

    La base MongoDB

    La base MongoDB est une base NoSQL orientée document. Elle comprend des collections, elles-mêmes contenant des documents semi-structurés semblables à des JSON. C'est le critère de variété du BigData qui est recherché ici.

    Les scripts s'organisent ainsi:

    • schemas_mongo.py définit les types des données exposées par l'API
    • crud_mongo.py contient toutes les fonctions CRUD appelées par l'API
    • sync_sql_mongo.py contient les scripts de synchronisation avec la BDD.

    La BDD

    La base de données est construite avec SQLAlcheny, permettant ainsi de changer de SGBDR sans grosse modification du code. Dans l'état actuel, la BDD créée est une base PostgreSQL.
    Cette sous-partie du projet est dans le répertoire E4/harmonie/BDD.
    La documentation SQLAlchemy se trouve à l'adresse: https://www.sqlalchemy.org/

    Les scripts s'organisent ainsi:

    • database.py établit les connexions aux bases de données et crée les sessions.
    • models.py définit les tables de la BDD
    • crud.py contient toutes les fonctions CRUD qui peuvent être exécutées directement mais qui sont aussi appelées par l'API ou encore le script d'alimentation de la BDD
    • create_db.py contient les scripts d'alimentation de la BDD à partir de fichiers .csv. La fonction insert_event_to_db() insère les événements dans la table du même nom, insert_scrapy_to_db() insère les données venant du scraping mais également de l'API musicbrainz.org, insert_users_to_db() insère de faux users pour tester l'API.

    L'API

    L'API REST est développée avec FastAPI. Documentation à l'adresse https://fastapi.tiangolo.com/learn/.
    Cette sous-partie du projet se trouve dans le répertoire E4/harmonie/BDD.
    Elle comprend les fichiers: + api_hbm.py. C'est le fichier principal qui appelle les contrôleurs de routes/ + schemas.py. Les classes Pydantic qui y sont déclarées permettent la validation des types de données et le formatage des réponses. + schemas_mongo.py. Equivalent pour les données provenant de Mongo. + auth.py contient les fonctions nécessaires pour mettre en place l'authentification. 3 variables sont définies dans le .env.
    SECRET_KEY = "09d25e094faa6ca2556c818166b7a9563b93f7099f6f0f4caa6cf63b88e8d3e7" ALGORITHM = "HS256" ACCESS_TOKEN_EXPIRE_MINUTES = 30
    Cette clé secrête est celle de la documentation FastAPI. Pour générer votre propre clé, exécuter la commande openssl rand -hex 32 dans un terminal.

    ainsi que le dossier routes/ qui lui-même contient: + associations.py + auteurs.py + authentification.py + evenements.py + instruments_dico.py + instruments.py + musiciens.py + partitions_details.py + partitions_hbm.py + partitions.py + regles_substitution.py + users.py*
    Chacun de ces fichiers contient toutes les fonctions d'API se rapportant au contrôleur du même nom.

    Pour démarrer l'API, il faut exécuter uvicorn api_hbm:app au niveau de E4/harmonie/BDD/
    Elle est visible pour l'instant à l'adresse http://127.0.0.1:8000/docs ou http://127.0.0.1:8000/redoc.

    Les DAGS

    Les DAGs associés à ces flux sont: - setup_hbm_dag.py -> crée la base, les tables, les alimentations avec le jeu de données initial - daily_events_update_dag.py -> récupère le fichier events.csv depuis un dépôt git (s'il a été mis à jour), le copie dans le data lake et l'ingère dans la BDD - daily_scrapy_update_dag.py -> lance le scraping, copie dans le data lake, nettoie, ingère les données directement (partitions) ou appelle l'API Musicbrainz (auteurs), les ingère dans la BDD + fichier de rejet - daily_synchro_dag.py -> synchronise la base Mongo avec la BDD

    L'exposition

    L'exposition se fait aux adresses https://DOMAIN_A_REMPLACER.ngrok-free.dev/api/docs ou https://DOMAIN_A_REMPLACER.ngrok-free.dev/api/redoc ou les équivalentes http://localhost:8000/docs et /redoc dans une configuration en local sans Ngrok.
